# M6: immediate selection and validated scalar stack caching

> **Retired (October 2026).** `--registers=local`, its cache
> (`amd64_cache.pl`) and its checker (`amd64_cache_check.pl`) were removed
> after the code-quality campaign ([perf.md](perf.md), register modes).
> Whole-function register homes with register operands and frame cells
> (`--registers=temps`, the `-O` default) do everything the cache did, on
> all eleven gate workloads, with fewer instructions and in less time
> (lz4 `-1` within noise):
> geomean 3.32× filcc `-O2` for `-O --registers=local`, 2.18× for `-O`.
> The cache's only trusted code of its own was its checker, so keeping it
> cost about a tenth of the Nix check and ten program builds for a mode
> nothing used. Immediate selection (below) is not retired: it is the
> allocating selection, `sel(local, …)` in `filc_amd64.pl`, that temps
> emits. A retired `--registers=local` is refused with an error. The
> diagnostic `tests/bench-registers.pl` with its kernel `bench-registers.c`,
> and the checker's attack suite
> `tests/cache_check.pl` went with it; they are at `7fc3fa2`. The rest of
> this page is the record of the milestone as it was.

`--registers=local` selects integer immediates, then caches scalar stack
homes. It is not general register allocation or completion of M6.
`--registers=stack` remains the default. Both work independently of `-O`;
build harnesses can set `NANOFIL_REGISTERS=local` instead. The plain SysV
backend is unchanged.

## Immediate selection precedes the cache's proof boundary

The opt-in `amd64:compute_op//5` selects immediate right operands for
`w/l` add, subtract, multiply, and/or/xor and the three shifts. It leaves
the reference `compute_op//4` unchanged. Constants normalize modulo the
operand width; a qword ALU immediate must equal a sign-extended imm32.
Thus `0xffffffff` can be immediate at `w` but not at `l`, where it means
positive 4294967295. All other cases retain register operands. Shifts mask
the constant count to 31 or 63 and retain even a zero-count instruction;
branches still test their operand explicitly, not the shift's flags.

Selection removes only the constant's scratch move to RCX. It retains
the LHS load, result width, operation, defined flags and result store.
Variable counts, division/remainder, comparisons, floats, pointer flight
operations, helpers and checks are unchanged. The Fil-C function context
carries the mode; setjmp forces reference selection before any emission.

The translation checker validates **caching of the selected stream**, not
old selection against new selection. Selection is trusted emitter code,
tested through emitted forms and native/interpreter/clang comparisons.
An unsupported machine form or original cache-bank use disables caching
of the whole implementation, retaining selected-but-uncached code. This
differs from setjmp, which bypasses both selection and caching.

## The machine contract bounds the transformation

`amd64_contract.pl` describes known instruction **forms**, including
register families and widths, explicit/implicit reads and writes, flags,
memory and control/frame effects. Division names its accumulator and high
half, variable shifts read `cl`, and partial writes retain their widths.
Any unknown original form or original use of the `r10/r11` bank selects
the uncached selected implementation. Calls may clobber both cache registers.
Call argument reads are not enumerated: calls are unconditional boundaries,
and ordinary registers remain equal. This is not a general call-liveness
model for future allocation passes.

`filc_amd64` supplies the original temporary classes and placed physical
homes before that information disappears. Every alias of an eligible
scalar home must be `w/l`. A home shared with `s/d`, an unknown class,
pointer payload/lower, phi shadow, local payload/aux, or frame bookkeeping
is not eligible. All eight bytes stay together: incoming `w` words can
have nonzero upper bits. A cold 32-bit read fills all 64 bits; its register
read still zero-extends into the original destination.

Only the implementation body is transformed. Getters, adapters, function
objects and origins retain their original lines and independent layouts.
Every setjmp function is unchanged, including one with only unreachable
setjmp sites. The middle end already preserves those complete functions.

## Regions preserve all existing boundaries

A region ends before every branch, call, label, directive, terminal,
frame-base/stack-pointer change, and every memory operation other than an
exact eligible frame load/store. This includes `leave`, **before** it
restores the caller's frame. Labels begin empty; no predecessor relies on
fallthrough cache contents. Unknown instructions are not merely barriers.

The conservative memory boundary covers partial/overlapping frame accesses,
indirect addressing and local payloads without an alias analysis. Helpers
inside pointer operations are ordinary call boundaries, regardless of
whether they usually exit. Phi reads into shadows, phi writes, polling,
rooted helper reloads and exception tests keep their original order.

`amd64_cache.pl` first removes loads whose complete result is already in
the destination register. It remembers one physical-home association per
register, invalidating it on register writes and invalidating every
association with a home on a store. A dword reload is removable only when
the destination's high half is already zero; a dword association alone
never justifies removing a qword reload. Boundaries forget all facts,
including zero-extension. Copies and partial writes remain opaque.

Then it groups a home's remaining first-to-last references in each region.
A deterministic linear scan assigns profitable intervals to `r10`, then
`r11`; an overlapping interval under pressure stays on stack. There is no
eviction or next-use heuristic. Every store updates the resident home
version. A first read fills the register, and the last reference writes
back a dirty home. All inserted and replacement instructions are
flag-preserving moves; no arithmetic instruction moves or changes.

This reduces memory transfers, not necessarily instructions. Two stack
moves can become two register moves plus a final spill. The pass retains
the frame allocation and every original scalar home.

## The checker validates the final instruction list

`amd64_cache_check:check_cache/3` derives eligible homes independently and
pairs the selected uncached and final cached streams. Only the three permitted
move forms may change; a load may also disappear if its complete result
equals the current ordinary register. This compares with the **reference**
home, not possibly stale candidate memory. Every other line must be
identical and ordered. It symbolically tracks ordinary register families,
full-width cache values,
and separate reference/actual home contents. Low/high halves distinguish
a 32-bit value from its full incoming word. Unchanged arithmetic gives
both streams the same fresh result, rather than reimplementing x86.

All homes must agree before every boundary. The checker then forgets
cache contents and uses fresh common symbolic entry values. Sparse maps
avoid rescanning the whole frame at every boundary. Inserted frame accesses
require the original prologue and cannot follow `leave`. Every fill must
immediately replace the next original load of the same home: establishing
`rbp` alone does not permit speculative reads before the stack-overflow
check. A failed check is a compiler error, not silent fallback. The checker
shares machine facts, not interval choices or claimed eligibility; it
derives eligibility from the emitter's trusted class/placement inventory.
An omitted load is consumed before trying a later fill's immediate anchor;
the fill itself never moves earlier. Matching is deterministic and still
checks raw input against final output, not only the intermediate cleanup.

## Validation and limits

The native differential, interop, GC, helper-exit, exception and setjmp
suites run with both register modes and both middle-end modes. GNU Hello,
zlib and Lua also build and run in all four combinations. The unchanged
stack mode has 1,030 byte-identical snapshot outputs against the preceding
correctness-fix commit.

Hand-authored checker cases reject omitted writebacks, stale values across
calls/labels, stale versions after ordinary stores, truncation of high
bits, changes to flags/failure registers/exception branches, float-shared
homes, unknown forms, and original cache-bank use. In-memory checker
mutations removing zero-extension or boundary synchronization are caught.
The speculative pre-overflow-check fill was accepted before the anchored-
fill rule and is now rejected. Backend tests establish actual integer/float
slot sharing and reject a mutation that misclassifies the float aliases.
Native mutations also exercise the previously scratch-only pointer-helper
and exception regressions; see [pizlonation.md](pizlonation.md).

The trust boundary remains the original emitter, complete class/placement
metadata, the audited machine forms, the checker and the assembler. This
does not prove the original compiler or Fil-C runtime correct. No pointer
allocation, reduced rooting, check/poll removal, cross-region allocation,
setjmp allocation or C++ unwinding is introduced.

## Redundant-load removal reduces instructions without widening allocation

This follow-up uses the same toolchain and orb. Its baseline is
[`76de0216`](https://github.com/mbrock/filnix/commit/76de0216adc20821b39b63c701076f2adfd9b555),
not the original stack backend. It follows Oracle's smaller proposal:
remove proven reloads before interval planning, with no copy propagation
or arithmetic rewrite. Instruction reduction is measured on the final
stream: replanning intervals can add other fills and writebacks.

Upstream informed the boundary, not an allocation algorithm. At the pinned
Fil-C source, Pizlonator leaves ordinary integer operations alone
([FilPizlonator.cpp](https://github.com/mbrock/fil-c/blob/af813053ecb5a5ff27292bfede8d3a9e870d4c8e/llvm/lib/Transforms/Instrumentation/FilPizlonator.cpp#L14718-L14742));
LLVM runs ordinary cleanup around instrumentation
([BackendUtil.cpp](https://github.com/mbrock/fil-c/blob/af813053ecb5a5ff27292bfede8d3a9e870d4c8e/clang/lib/CodeGen/BackendUtil.cpp#L1050-L1140)).
Nanofil likewise keeps safety lowering separate from scalar cleanup.
It does not adopt upstream KillUB's division semantics: original native
arithmetic and faults remain unchanged.

Thirty GDB samples per Lua workload put 59 of 60 samples in
`luaV_execute`. Its assembly includes result/store/reload sequences, but
this coarse sampling does not attribute a percentage of time to them.
Thirty zlib text-compression samples landed in `longest_match` (23) and
`deflate_slow` (7); `longest_match` also contains the same store/reload
pattern, among many pointer operations that remain untouched.
`lvm.c` below is Lua 5.4.7 with the gate's switch-dispatch flags. The kernel
is [bench-registers.c](../tests/bench-registers.c), two loop-carried unsigned
32-/64-bit chains with runtime count and seed, not a dead-code benchmark.

runs pass after these mutations. Stack still has 1,030 byte-identical
snapshot outputs; both stack Lua binaries are byte-identical too.

## Immediate selection: fewer instructions with the same frame traffic

This experiment's baseline is
[`a3c1269`](https://github.com/mbrock/filnix/commit/a3c12692f686b1cdaa290365f903e8a908ef90ef),
including redundant-load removal, not the original stack backend. Oracle
reviewed the immediate selector's width rules, scratch-register contract
and proof boundary before adoption. Its two-operand immediate `imul` form
was assembled and disassembled: GNU as encodes the accumulator as both
source and destination, without an RDX result.

The previously sampled hot functions contain actual adjacent constant-to-
RCX moves followed by arithmetic or shifts through CL. In `luaV_execute`
there are 1,421 encodable arithmetic pairs and 707 shifts; `longest_match`
has nine and one; the kernel loop and increment have six and ten. The
candidate converts all of them, leaving unencodable qword constants alone.
These counts were checked independently in the assembled objects. They
describe entire function implementations, not dynamic execution counts.
