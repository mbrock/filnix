Frame slot coloring at -O0: from cubic to near‑linear

Where it showed up

The work behind this was an experiment in retargeting PHP's opcache JIT to Fil-C. The JIT's IR is printed as C, compiled with Fil-C's clang, and loaded with dlopen, the same approach as Emacs' native-compilation backend on Fil-C. JIT traces become long, branchy functions: guard, guard, overflow-checked add, call a helper, repeat. At -O1 such a function compiled in well under a second. At -O0 the time grew steeply with function size: 0.8 s for 40 blocks, 4.7 s for 80, 48 s for 160, and 597 s with 2.8 GB of memory for 300.

-ftime-report put 99.6% of cc1's time in FilPizlonatorPass (8.81 of 8.96 s at 80 blocks). perf put most of that in computeFrameIndexMap and its FrameEntry hash lookups. The abstract interpreter and the check scheduling were not the cause.

What computeFrameIndexMap does

Every instrumented function pushes a filc_frame, and that frame ends in a lowers[] array. Whenever the function holds a pointer that FUGC must see while it scans the stack, the pointer's capability (its lower) sits in a slot of that array. Naked local allocas, the ones without a header, mirror their stack aux into a slot as well.

The pass gives every pointer-bearing value a slot index. Two values can share a slot if they are never live at the same time. So the pass computes liveness, builds an interference graph, and colors it greedily: it visits values in a fixed order (arguments, then instructions in block order) and gives each the lowest slot that no already-colored neighbor holds. This is register allocation with an unlimited register file, where the goal is a small frame.

Why -O0 blows up

A static alloca that is small enough and doesn't escape becomes LocalNaked. If it has no lifetime markers, it also goes into AlwaysLive. Optimized builds give most locals llvm.lifetime.start/end, which bound their live ranges. Clang emits no lifetime markers at -O0, so every local is AlwaysLive. The old code made them live like this:

// Make sure that AlwaysLive allocas are always live. This is very hacky, but is obviously
// correct.
for (BasicBlock* BB : Blocks)
  for (Instruction& I : *BB)
    if (AllocaInst* AI = dyn_cast<AllocaInst>(&I))
      if (AlwaysLive.count(AI))
        for (auto& Pair : LiveAtTail)
          Pair.second.insert(&I);   // into every block's live set

That really is correct. The cost shows up in the next two steps:

  1. Building the graph. The backward walk adds an edge from each defined value to everything live. With A always-live allocas and P pointer values, the allocas form a clique and each of them is adjacent to every value: about A·(A/2 + P) edges, each stored twice in an unordered_set.
  2. Coloring it. For each candidate slot, the old picker scanned the value's whole adjacency list, looking for a colored neighbor that holds that slot. A pointer value starts at slot 0 and collides with an alloca at each of the first A slots. Every collision costs a scan through an adjacency list of at least A entries, so the total is about P·A²/2 neighbor checks.

The 160-block test function has A = 803 and P = 4,647, which works out to about 4 million edges and about 1.5 billion hash lookups to place the values. Doubling the function multiplies the time by roughly 8 to 12.

The observation

Static allocas live in the root block. An always-live naked alloca there is live everywhere except above its own definition. Take the always-live root allocas in root-block order and call them RootAlwaysLive. At any program point, the live ones are exactly those defined above that point, which is always a prefix of the list.

The coloring visits the root block first, in the same order. So when it reaches a value, the root allocas it has already colored are the ones live where that value is defined. Inside the root block that is a prefix, and everywhere else it is all of them. The new code therefore doesn't record those edges at all. It keeps one growing set of slots taken by colored root allocas, and every value avoids that set.

Liveness walks backward; coloring walks forward

Values defined later never free a slot in that set, so the set only grows. It tracks its first missing index, and the slot search starts there:

// A growing set of frame indices that knows its lowest missing index.
struct FrameIndexSet {
  std::vector<bool> Contains;
  size_t FirstMissing { 0 };
  void add(size_t Index) { /* set the bit; advance FirstMissing past set bits */ }
};

Picking a slot also changes. Instead of rescanning the adjacency list for every candidate, the picker makes one pass that stamps each colored neighbor's slot with an epoch number. Then it scans upward from max(Begin, Taken.FirstMissing) for the first slot that is neither taken nor stamped. One pick costs O(degree + distance to the answer) instead of O(answer × degree).

Two corner cases

A lifetime start after later allocas

A root alloca m with lifetime markers can come before an always-live alloca a in root order while its lifetime.start comes after a. At that start, m is defined where a is live, so the two interfere. But m is colored first, and when a is colored afterwards, nothing tells it to avoid m. For a lifetime start, the walk therefore records real edges to the live root allocas that come after the alloca in root order, the range [NumRootAlwaysLiveBefore[m], NumLiveRootAlwaysLive). Choose corner case above to watch those edges appear in red. The test corpus hit this path in 1,430 functions.

Explicit locals and stack aux slots

LocalExplicit allocas get stack aux slots above FrameSize. An always-live one must interfere with every other explicit local. Otherwise they all share one slot, and the collector only sees whichever stack aux was initialized last. The old code wrote that rule as all-pairs edges. The new code keeps two sets of slots instead: the slots of every explicit local colored so far, and the slots of the always-live explicit locals colored so far. An always-live local avoids the first set. Any other local avoids the second set plus its ordinary liveness neighbors. The rule is symmetric, so this forbids the same slots as the all-pairs edges at every step.

Why the layout is identical

The new code doesn't approximate the old graph. It claims a stronger invariant: before each coloring decision, old and new forbid exactly the same set of slots. The decision for each node is the lowest slot outside that set, so by induction on the coloring order, every slot assignment is identical. The proof of that invariant is the prefix argument plus the lifetime-start exception. Debug builds also check the prefix directly: assert(Iter->second + 1 == NumLiveRootAlwaysLive) fires if a root alloca's definition is ever reached other than at the end of the live prefix.

The fix was also checked empirically. A temporary compiler carried the original function as computeFrameIndexMapReference. It ran both versions on every function and compared FrameIndexMap (entry kind and index), FrameSize, NumStackAuxes, and the setjmp and vararg slots, aborting on any difference. It ran over:

  • every C and C++ file in filc/tests, at -O0, at -O2, and at -O1 -mllvm -opt-bisect-limit=0 (lifetime markers but no optimization);
  • generated traces of 10, 40 and 80 blocks in all three modes;
  • directed cases: entry values before allocas, more than 64 slots, multiword objects, local arrays, lifetime markers in scopes and loops, goto and unreachable blocks, setjmp, varargs, and memcpy.

The result was 44,006 functions identical and 0 different, with frames of up to 487 slots. A separate reviewer checked the induction and looked for counterexamples in normal pipelines (repeated lifetime starts, unreachable and non-entry blocks, multi-pointer values, ignored entries, zero-slot allocas, values outside Order) and found none. That review also caught two problems in a first draft that used llvm::BitVector, which are fixed in the final version. Its find_first_unset_in returns an int over unsigned sizes, and copying the vector for each node brought back quadratic work.

That comparison ran in the fork. The commit then cherry-picked cleanly onto upstream deluge at 9d1ed206. Upstream's only change near this code gives each setjmp call its own frame slot, and those slots are appended after the coloring. With assertions enabled, the rebased compiler built 7,836 translation units from filc/tests at -O0 and -O2. None hit the prefix assertion. The only crashes were the badasm tests, which are meant to fail.

What's left

After the fix, both -O0 and -O1 still grow a bit faster than linearly, but no single hot spot dominates the profile. At 600 blocks FilPizlonator is about 31% of compile time, and scheduleChecks (its set-based canonical-pointer liveness) is about 16%. The change leaves that code alone because touching it could change where checks are placed. One unrelated fix rides along: removeRedundantChecksUsingForwardAI now takes CanonicalPtrLiveAtTail by const&. It used to take it by value, which copied every block's live set twice per function.

The change is a single commit to llvm/lib/Transforms/Instrumentation/FilPizlonator.cpp (+137 −61), on top of pizlonator/fil-c deluge. This page was written for review and is not part of the patch.
